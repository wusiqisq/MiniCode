# MiniCode 初步设计

本文记录当前设计方向。实现细节可在相应阶段调整，重要变化应说明理由。

## MVP 与边界

MVP（最小可行产品）的目标：在指定项目中理解一个小型修改任务，读取相关文件，提出修改，经用户确认后写入，执行批准的测试命令，并汇报结果。

第一版采用单用户、单项目、单模型、同步顺序执行。会话只保存在进程内；退出后不恢复。核心 Agent Loop 自行实现。

暂缓复杂全屏界面、多 Agent、后台任务、多模型切换、向量数据库、长期记忆、插件，以及自动 Git 提交和推送。

## 核心组件

| 组件 | 职责 |
| --- | --- |
| CLI（终端入口） | 收集输入，展示结果与授权问题 |
| Agent Loop（循环控制器） | 调用模型、处理工具请求、执行停止规则 |
| Model Client（模型客户端） | 与模型服务通信，解析回复和工具请求 |
| Session（会话状态） | 保存消息、工具结果和执行计数 |
| Tool Registry（工具注册表） | 保存工具名称、参数说明和对应函数 |
| Tools（工具） | 读取、搜索、编辑文件，执行命令 |
| Permission Policy（权限规则） | 判断允许、拒绝或需要用户确认 |

初期用简单函数和数据结构表达职责，不要求每个组件都设计成类。计划中的模块包括 `cli.py`、`config.py`、`models.py`、`session.py`、`llm.py`、`agent.py`、`permissions.py` 和 `tools/`，随功能加入，不提前创建空壳。

`models.py` 表达内部数据结构，`llm.py` 负责外部模型调用。可安装代码放在 `src/minicode/`，测试放在 `tests/`。

## Agent Loop 的运行过程

1. 将用户输入加入会话。
2. 将消息和工具说明交给模型。
3. 模型返回最终回复，或者结构化的工具请求。Function Calling 表示工具请求，本身不执行函数。
4. 校验工具名称与参数，检查安全边界和权限。
5. 必要时请求用户确认；拒绝时生成明确的拒绝结果。
6. 执行获准工具，将结果与请求标识对应后加入会话。
7. 再次调用模型，根据结果继续行动。
8. 返回最终回复或停止原因。

消息区分用户、助手和工具；应用规则单独提供。一次返回多个工具请求时按顺序处理。工具结果应能表达成功、失败、拒绝和输出截断。

停止条件包括模型给出最终回复、调用次数达到上限、连续失败达到上限、模型请求无法继续，以及用户中断。达到限制不等于任务成功，必须说明未完成状态。具体上限在实现阶段确定。

## 安全边界

- 读取与搜索限制在项目范围，默认排除敏感文件并限制内容大小。
- 编辑需展示路径与差异，逐次确认；写入前检查外部修改，避免覆盖。
- 命令需展示参数、工作目录和超时，逐次确认；收集退出码、标准输出与标准错误。
- 初版不提供独立删除工具或自主 Git 提交、推送工具。
- 文件和命令输出只是数据，不能覆盖权限规则。
- 命令的工作目录不能限制程序的全部文件或网络访问。初版不是安全沙箱，仅面向用户监督下的可信项目；隔离执行另行设计。

## 技术选择

| 技术 | 初步选择与理由 |
| --- | --- |
| 语言 | Python 3.11+；已在 Python 3.12.3 验证 |
| 环境 | `venv` 与 `pip`，先掌握环境和依赖基础 |
| 配置 | `pyproject.toml`，在创建程序骨架时加入 |
| 模型通信 | HTTPX 同步调用 DeepSeek `/chat/completions`；默认 `deepseek-flash`，非流式、关闭思考模式，每次最多输出 1024 tokens |
| 模型配置 | python-dotenv 读取当前工作目录 `.env`，已有环境变量优先；配置密钥、模型、HTTPS 基础地址与网络操作超时 |
| 内部数据 | 优先标准库 `dataclasses` 和简单类型标注 |
| 多轮会话 | `Session` 保存按 user / assistant 顺序排列的消息列表；请求包含历史副本和当前问题，成功后记录整轮，失败不记录；`/clear` 清空，退出不持久化 |
| 文件与命令 | `pathlib` 和 `subprocess` |
| 测试 | pytest；模型响应默认使用可控的测试替身 |
| 终端 | 先使用 `input()` 和 `print()`，之后再改善交互 |
| 版本管理 | Git，阶段性练习分支和 PR |

暂不引入异步框架、数据库、通用多服务商适配层或完整 Agent 框架。

## 开发里程碑

以下是顺序路线，不代表单次任务要完成整个阶段。每次开发仍需明确小范围与验收条件。

| 阶段 | 交付内容 | 核心验证 |
| --- | --- | --- |
| 1 | 项目骨架与最小终端交互 | 启动、普通输入、空白、退出与中断 |
| 2 | 单次模型调用 | 响应、缺少密钥、超时和服务错误 |
| 3 | 进程内多轮对话 | 历史正确、支持清空会话 |
| 4 | 受限文件读取 | 正常读取、越界与敏感路径、大小限制 |
| 5 | 工具注册与 Function Calling | 正确分发，非法工具和参数不执行 |
| 6 | Agent Loop | 连续工具调用，失败和次数限制 |
| 7 | 项目搜索与上下文限制 | 定位内容、输出受控 |
| 8 | 经确认的编辑 | 差异可见，拒绝不写入，冲突不覆盖 |
| 9 | 经确认的命令执行 | 退出码、输出、拒绝与超时终止 |
| 10 | 测试与有限修复闭环 | 在小型示例项目中修改、测试、修复并汇报 |
| 11 | 终端体验与发布准备 | 安装说明可复现，行为和限制清晰 |

权限规则从第一个文件工具开始加入，不能等到后期统一补上。

## 第一阶段验收标准

第一阶段不接模型 API，不执行用户项目文件操作。

- 在独立虚拟环境中可以安装项目。
- `python -m minicode` 可以启动。
- 普通输入得到明确提示，说明模型功能尚未接入，并继续等待。
- 空白输入不产生任务；`/exit` 和 EOF 正常退出。
- Ctrl+C 结束程序并给出简短提示，不展示异常堆栈。
- 自动化测试覆盖以上行为；`python -m pytest` 通过且无需网络或密钥。
- README 中的安装、启动、测试命令经过实际验证。
- 提交前检查差异，排除密钥、缓存和虚拟环境。

## 第二阶段验收标准

- 从当前目录 `.env` 或环境变量读取 DeepSeek 配置，已有环境变量优先；不展示密钥。
- 输入问题后，以同步 HTTP 请求发送当前问题并展示文本回答，不保留对话历史。
- 空白和退出不发请求；等待模型时 Ctrl+C 可以正常结束程序。
- 缺少密钥、无效配置、超时、网络和 HTTP 服务错误有简短提示；失败后可以继续输入，不自动重试。
- 响应格式错误、空回答、长度截断或其他非正常结束不可作为完整回答显示。
- 自动化测试使用模拟响应，不访问真实 API、不读取用户密钥；真实调用单独验证。

接口依据：[官方快速开始](https://api-docs.deepseek.com/)、[Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/)、[错误码](https://api-docs.deepseek.com/quick_start/error_codes/)。

## 第三阶段验收标准

- 每次启动创建独立的进程内会话；第二轮请求按顺序包含上一轮用户问题、助手回答和当前问题。
- 仅在模型成功返回完整文本后保存整轮；配置、网络、服务或响应错误不留下未完成的问答，之前的成功历史不丢失。
- 构造请求使用消息副本，外部修改请求不会改变已保存历史。
- `/clear` 清空本地历史，不读取配置、不请求模型；空历史也可反复清空。
- 空白、清空和退出命令不进入历史；退出后不写入磁盘、不恢复会话。
- 离线测试直接检查 HTTP 请求的消息列表，覆盖多轮顺序、失败后继续、清空后新对话和重新启动。
- 当前不裁剪历史、不计算 token；上下文限制留待后续阶段处理，长对话可用 `/clear` 重置。
